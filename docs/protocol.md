# Wire protocol — chat-service

Status: **draft v0.1** (owner: Backend, reviewer: Frontend). Any change goes through a reviewed PR;
nobody changes this file silently. Decision IDs refer to the design doc's ledger.

This is the contract between `chat-service` and its clients (Angular `chat-web`, the Node `chaos/`
client and the Java `StompTestClient`). It covers STOMP over WebSocket, REST, error codes, receipts,
paging and the dev token issuer.

## 1. Conventions

| Item | Rule |
|---|---|
| Encoding | UTF-8 JSON, `content-type: application/json` on every STOMP body and REST body |
| Field names | camelCase on the wire; enum **values** are the database values (French, AR04 style) |
| Ids | `conversationId` / `id`: JSON number (BIGSERIAL, < 2^53). `seq`: JSON number, starts at 1, gap-free per conversation |
| Client ids | `clientMessageId`, `clientRequestId`: UUID strings generated by the client (v4 or v7) |
| Timestamps | ISO-8601 UTC with milliseconds, e.g. `"2026-10-19T10:15:30.123Z"` |
| Absent values | `null` (never omitted) |
| Identity | from the JWT only: `sub` → `customerRef` / `agentRef` / `senderRef`; `role` → actor kind |

Enums:

| Enum | Values |
|---|---|
| conversation `status` | `en_attente` (waiting in queue) · `en_cours` (claimed by an agent) · `cloturee` (closed) |
| `customerKind` | `compte` (logged-in customer) · `invite` (guest) |
| item `type` | `texte` (chat message) · `prise_en_charge` (claim event) · `cloture` (close event) |
| item `senderRole` | `client` · `agent` · `systeme` (always `systeme` for `prise_en_charge` / `cloture`) |
| JWT `role` | `customer` · `guest` · `agent` (`customer`/`guest` are both "customer actors"; `guest` → `customerKind = invite`) |

## 2. Shared JSON shapes

### 2.1 `Conversation`

```json
{
  "id": 42,
  "status": "en_cours",
  "customerRef": "customer-1",
  "customerKind": "compte",
  "reservationReference": "YCYW-2026-000123",
  "agentRef": "agent-1",
  "lastSeq": 7,
  "createdAt": "2026-10-19T10:00:00.000Z",
  "claimedAt": "2026-10-19T10:01:00.000Z",
  "closedAt": null
}
```

`agentRef` is non-null whenever `status = en_cours`; it may be null for `cloturee` (a customer can
close an unclaimed conversation, A4).

### 2.2 `Item` (one sequenced entry of a conversation stream)

Same object on the conversation topic and in REST backfill.

```json
{
  "conversationId": 42,
  "seq": 7,
  "clientMessageId": "0b6f3c8e-5a8e-4d0e-9a39-0d4cf0e6f6a1",
  "type": "texte",
  "senderRole": "client",
  "senderRef": "customer-1",
  "content": "Bonjour, ma voiture n'est pas au point de retrait.",
  "createdAt": "2026-10-19T10:02:00.000Z"
}
```

System events (C3): `type` = `prise_en_charge` or `cloture`, `senderRole = "systeme"`,
`content = null`, `clientMessageId` = a server-generated UUID, `senderRef` = the acting user
(`prise_en_charge`: the claiming agent; `cloture`: whoever closed it — compare with
`Conversation.customerRef` / `agentRef` to tell who). Conversation status is derived from these events,
so it is recovered by the same backfill as messages.

### 2.3 `ApiError` (REST error body)

```json
{ "code": "ALREADY_CLAIMED", "reason": "Conversation 42 is already claimed" }
```

`reason` is a human-readable English diagnostic, not meant for display; the UI maps `code` to its own
FR/EN strings.

## 3. STOMP over WebSocket

### 3.1 Endpoint and connection

| Item | Value |
|---|---|
| URL | `/ws` (native WebSocket, no SockJS). Demo-only first-connection pins: `/ws-a` → chat-1, `/ws-b` → chat-2 (C5); every **re**connect uses `/ws` |
| Protocol | STOMP 1.2 (`accept-version:1.2`) |
| Origin | handshake rejected with HTTP 403 unless `Origin` is in `chat.allowed-origins` (compose: the nginx origin) (A7) |
| Readiness | handshake answers HTTP 503 while the instance's `LISTEN` connection is not active; nginx then retries the other instance (A3/F9) |
| Frame size | inbound STOMP frames limited to 16 KB; larger → the server closes the session (A7) |
| Heart-beats | server offers `10000,10000`; clients should send `heart-beat:10000,10000` |

### 3.2 CONNECT

Client headers:

```
CONNECT
accept-version:1.2
heart-beat:10000,10000
Authorization:Bearer <jwt>
```

The token is validated **at CONNECT only** (RS256 signature with the configured public key, `iss`,
`aud`, `exp`). A session is not cut when its token expires later (A5, documented simplification).

Success → `CONNECTED` with these headers (in addition to the standard `version`, `heart-beat`):

| Header | Example | Use |
|---|---|---|
| `instance-id` | `chat-1` | instance badge (C5) |
| `user-name` | `customer-1` | the JWT `sub` as seen by the server |

Failure → `ERROR` frame, then the server closes the connection:

| `message` header | Body (first token = the code) | When | Client action |
|---|---|---|---|
| `TOKEN_EXPIRED` | `TOKEN_EXPIRED Token expired at 2026-…Z` | `exp` in the past | renew via `POST /dev/tokens` (same `role` + `subject`), reconnect (A5) |
| `UNAUTHORIZED` | `UNAUTHORIZED <reason>` | missing / malformed header, bad signature, wrong `iss`/`aud` | do not retry blindly; get a new token |

**Every frame other than CONNECT on a not-yet-authenticated session** (SEND, SUBSCRIBE, …) gets
`ERROR` `message:UNAUTHORIZED` and the connection is closed (A7).

### 3.3 Destinations

| Destination | Direction | Who | Receipt (O7) | Payload |
|---|---|---|---|---|
| `/topic/conversations/{id}` | server → client | actors allowed by the access policy (§5) | **yes, required** | `Item` |
| `/topic/queue` | server → client | agents only | **yes, required** | `QueueEvent` (§3.6) |
| `/user/queue/acks` | server → client | any authenticated session | no | `Ack` (§3.5) |
| `/user/queue/errors` | server → client | any authenticated session | no | `SendError` (§3.5) |
| `/app/conversations/{id}/messages` | client → server (SEND) | participants (§5) | no (application ack instead) | `SendMessage` |

Any other SUBSCRIBE or SEND destination (in particular SEND to `/topic/**`) → `ERROR`
`message:FORBIDDEN` and the connection is closed. A SUBSCRIBE refused by the access policy
(not a participant / not visible) → `ERROR` `message:NOT_FOUND`, connection closed; the `ERROR` carries
`receipt-id` when the SUBSCRIBE had a `receipt` header.

### 3.4 SUBSCRIBE and RECEIPT rules (A1, O7)

```
SUBSCRIBE
id:sub-42
destination:/topic/conversations/42
receipt:r-42-1
```

- Clients put a `receipt` header on every `/topic/**` SUBSCRIBE and **not** on `/user/queue/**`
  (the server never sends a RECEIPT for those).
- **Requirement** (not assumption): the `RECEIPT` (`receipt-id:r-42-1`) is emitted only after the
  subscription is registered in this instance's broker, so any item committed after the client
  receives the RECEIPT is delivered live on this subscription. Verified by integration test 4e.
- Client procedure on every (re)connect: subscribe `/user/queue/acks` + `/user/queue/errors`,
  then SUBSCRIBE each topic with a receipt → on RECEIPT start the backfill `afterSeq=lastSeq` (§4.6);
  no RECEIPT within 5 s → close and reconnect. Safety net: a second backfill 2 s after every
  (re)subscribe (idempotent through seq dedup).
- Agents: on RECEIPT for `/topic/queue`, call `GET /api/conversations?status=en_attente` and **replace**
  the local queue.

### 3.5 SEND, ack and error

```
SEND
destination:/app/conversations/42/messages
content-type:application/json

{"clientMessageId":"0b6f3c8e-5a8e-4d0e-9a39-0d4cf0e6f6a1","content":"Bonjour"}
```

Server processing (one transaction, A2): lock conversation → if `(conversationId, clientMessageId)`
already exists and was sent by the same user → **ack with the existing seq** (no new item, no NOTIFY;
`content` of the retry is ignored) → else access / closed / content checks → next seq → insert → NOTIFY
→ commit → ack.

Ack, on `/user/queue/acks` (sent to the **sending session** only; new message or idempotent retry):

```json
{ "conversationId": 42, "clientMessageId": "0b6f3c8e-…", "seq": 7 }
```

Error, on `/user/queue/errors` (sending session only; no row was written):

```json
{ "conversationId": 42, "clientMessageId": "0b6f3c8e-…", "code": "CONVERSATION_CLOSED", "reason": "…" }
```

| `code` | Meaning |
|---|---|
| `CONVERSATION_CLOSED` | conversation is `cloturee` and this `clientMessageId` was not stored before the close |
| `NOT_FOUND` | conversation does not exist or is not visible to this user (§5) |
| `FORBIDDEN` | visible but this user may not post (agent on an unclaimed conversation, or the `clientMessageId` belongs to another sender) |
| `INVALID_CONTENT` | `content` null, blank, or not 1–2000 characters (Unicode code points, same as PostgreSQL `char_length`) |
| `INVALID_REQUEST` | body is not valid JSON, or `clientMessageId` missing / not a UUID (`clientMessageId` may then be `null`) |

Rules for clients:
- The ack only clears the outbox entry (C2). The message is displayed at its seq when the `Item`
  arrives on the topic or via backfill (deduplicated by seq / `clientMessageId`).
- Acks can legitimately repeat for the same `clientMessageId` (retries); they always carry the same seq.
  Ignore acks/errors for unknown `clientMessageId`s.
- Content length is also validated client-side before sending.

### 3.6 Conversation topic and queue topic

`/topic/conversations/{id}`: every `Item` of the conversation (`texte`, `prise_en_charge`, `cloture`),
in seq order per instance (`setPreservePublishOrder`, O9). Clients still buffer by seq and fetch gaps
(C1): items may be missing after a reconnect, never reordered within one live subscription.

`/topic/queue` (agents only), **unsequenced**:

```json
{ "t": "opened", "conversationId": 42, "conversation": { …Conversation… } }
```

`t` ∈ `opened` · `claimed` · `closed`. `conversation` is the conversation **as read when the event was
published** (it may already be newer than `t`). Apply it as: `status == en_attente` → upsert into the
queue, otherwise remove. Using it purely as a refetch trigger is also correct. After a reconnect the
queue is recovered by `GET /api/conversations?status=en_attente`, never from missed events.

### 3.7 Server-initiated close

When an instance loses its LISTEN connection, fails its liveness check, or fails to load/publish an
item after a NOTIFY (A3, O1), it closes **all** its WebSocket sessions (close code `1012`, service
restart) and refuses handshakes (503) until its listener is back. Clients treat any close like a lost
connection: reconnect with exponential backoff + jitter, re-subscribe with receipts, backfill, resend
the outbox.

## 4. REST

Base path `/api`. Every request carries `Authorization: Bearer <jwt>`. Every response carries
`X-Instance-Id: chat-1` (debug). REST does not depend on the LISTEN connection, so it keeps answering
while the instance refuses WebSocket handshakes.

Common errors (`ApiError` body):

| HTTP | `code` | When |
|---|---|---|
| 400 | `INVALID_REQUEST` | malformed JSON, invalid UUID, invalid query parameter |
| 401 | `TOKEN_EXPIRED` | `exp` in the past → renew and retry |
| 401 | `UNAUTHORIZED` | missing or invalid token |
| 403 | `FORBIDDEN` | conversation visible but the action is not allowed for this actor/state (§5) |
| 404 | `NOT_FOUND` | conversation does not exist or is not visible to this actor (§5) — never 403, so ids cannot be probed |
| 409 | `ALREADY_CLAIMED` | claim of a conversation that is no longer `en_attente` (claimed by someone else, or closed) |
| 409 | `CONVERSATION_CLOSED` | close of an already closed conversation |

### 4.1 `POST /api/conversations` — open (customer / guest only), idempotent (A6)

Request:

```json
{ "clientRequestId": "6f1d…", "reservationReference": "YCYW-2026-000123" }
```

`reservationReference` optional (`null` or absent; max 64 chars). For a `guest` token without one in the
body, the token's `reservation_reference` claim is used. `clientRequestId` is required: reuse the same
value when retrying the same "open" action.

- `201 Created` + `Conversation` (new, `en_attente`, `lastSeq = 0`) + `Location: /api/conversations/{id}`.
- `200 OK` + the **existing** `Conversation` when this user already used this `clientRequestId`
  (whatever its current status; the body's `reservationReference` is then ignored).
- `403 FORBIDDEN` for agents.

### 4.2 `GET /api/conversations?status=en_attente` — agent queue (P1)

Agents only (customers → 403). Response: the **oldest 50** waiting conversations, oldest first, and the
total count:

```json
{ "items": [ { …Conversation… } ], "total": 73 }
```

### 4.3 `GET /api/conversations` — "my conversations"

- Customer / guest: own conversations, newest first, max 50.
- Agent: conversations this agent claimed that are still `en_cours`, newest first, max 50.

Response `{ "items": [Conversation], "total": n }`. Other `status` values than `en_attente` → 400.

### 4.4 `GET /api/conversations/{id}`

`200` + `Conversation` if visible (§5), else `404`.

### 4.5 `POST /api/conversations/{id}/claim` — agents only

Conditional update `WHERE status = 'en_attente'`: first agent wins, appends a `prise_en_charge` item
(same transaction, NOTIFY) and emits a `claimed` queue event.

- `200` + `Conversation` (`en_cours`, `agentRef` = caller). Repeating the claim as the same agent on
  a conversation it already holds returns `200` again with no new item.
- `409 ALREADY_CLAIMED` if it is `en_cours` (another agent) or `cloturee`. This is the only endpoint where
  an agent learns that a conversation it cannot see exists: the loser of a race must get 409, not 404.
- `403` for customers on their own conversation, `404` if the id does not exist / customer on someone
  else's.

### 4.6 `POST /api/conversations/{id}/close` (A4)

Customer may close from `en_attente` or `en_cours`; the claiming agent from `en_cours`. Appends a
`cloture` item (same transaction, NOTIFY) and a `closed` queue event.

- `200` + `Conversation` (`cloturee`).
- `409 CONVERSATION_CLOSED` if already closed; `403` / `404` per §5.

### 4.7 `GET /api/conversations/{id}/messages?afterSeq=N[&limit=L]` — backfill (P1)

`afterSeq` default 0; `limit` default and max 200. Items with `seq > afterSeq`, ascending, at most
`limit`:

```json
{ "items": [ { …Item… } ], "hasMore": true }
```

Clients page with `afterSeq = last item's seq` until `hasMore = false` (one fetch in flight per
conversation, C1). Example: 450 items → pages of 200, 200, 50.

## 5. Access policy (O4, A4)

One `ConversationAccessPolicy` serves SUBSCRIBE, SEND and every REST endpoint.

Visibility: a customer/guest sees **only its own** conversations (`customerRef = sub`); an agent sees
conversations `en_attente` and the ones **it** claimed (any later state). Anything not visible → 404
(`NOT_FOUND` on STOMP).

| Actor \ action | read (GET, messages, SUBSCRIBE topic) | SEND message | claim | close |
|---|---|---|---|---|
| owner customer, `en_attente` | ✓ | ✓ | 403 | ✓ |
| owner customer, `en_cours` | ✓ | ✓ | 403 | ✓ |
| owner customer, `cloturee` | ✓ | `CONVERSATION_CLOSED` | 403 | 409 |
| other customer, any state | 404 | `NOT_FOUND` | 404 | 404 |
| any agent, `en_attente` | ✓ | `FORBIDDEN` | ✓ (race: one 200, others 409) | 403 |
| claiming agent, `en_cours` | ✓ | ✓ | 200 (idempotent) | ✓ |
| claiming agent, `cloturee` | ✓ | `CONVERSATION_CLOSED` | 409 | 409 |
| other agent, `en_cours` / `cloturee` | 404 | `NOT_FOUND` | 409 | 404 |
| agent on `/topic/queue` | ✓ | — | — | — |
| customer on `/topic/queue` | `FORBIDDEN` | — | — | — |

Send idempotency wins over every check except visibility: a retry of a message already stored by the
same sender is acked even if the conversation was closed meanwhile (A2).

## 6. Dev token issuer (`auth-stub`, A5)

Dev-only stand-in for the monolith's token issuer. Reached through nginx at `/dev/tokens`.

### 6.1 `POST /dev/tokens`

Request:

```json
{ "role": "guest", "subject": "guest-ab12", "name": "Alice", "email": "alice@example.com",
  "reservationReference": "YCYW-2026-000123", "ttlSeconds": 28800 }
```

| Field | Required | Default / rule |
|---|---|---|
| `role` | yes | `customer` · `guest` · `agent` |
| `subject` | no | generated `<role>-<8 hex>`; pass the previous one to renew the **same** identity |
| `name` | no | display name, defaults to `subject` |
| `email` | no | guests only, informative |
| `reservationReference` | no | guests: recommended (guest = reservation reference + email) |
| `ttlSeconds` | no | default 28800 (8 h), allowed 1–28800 (short values let clients test renewal) |

Response `200`:

```json
{ "token": "eyJ…", "tokenType": "Bearer", "expiresAt": "2026-10-19T18:00:00.000Z",
  "subject": "guest-ab12", "role": "guest" }
```

Invalid body → `400 { "code": "INVALID_REQUEST", "reason": "…" }`.

### 6.2 Token (RS256 JWT)

Header: `alg: RS256`, `kid`. Claims: `iss` (`ycyw-auth-stub`), `aud` (`ycyw-chat`), `sub`, `role`,
`name`, `email` (guest, optional), `reservation_reference` (guest, optional), `iat`, `exp`, `jti`.
chat-service verifies the signature with a **public key read from configuration** (premise 3: it never
calls the issuer at runtime).

## 7. Flows

Customer:
1. `POST /dev/tokens {role:"customer"}` → token (kept in `sessionStorage` with its `subject`).
2. `POST /api/conversations {clientRequestId}` → `Conversation` (retry with the same id on failure).
3. Connect `/ws` (demo `/ws-a`), CONNECT → `CONNECTED instance-id`.
4. SUBSCRIBE acks + errors, SUBSCRIBE `/topic/conversations/{id}` with receipt → RECEIPT → backfill.
5. SEND messages; outbox cleared on ack; items rendered from the topic/backfill.

Agent:
1. Token `{role:"agent"}`; connect; SUBSCRIBE acks + errors, `/topic/queue` with receipt → RECEIPT →
   `GET /api/conversations?status=en_attente` replaces the queue.
2. `POST /api/conversations/{id}/claim` → 200 → SUBSCRIBE `/topic/conversations/{id}` with receipt →
   RECEIPT → backfill from 0. 409 → remove from the queue.
3. Converse; `POST …/close` when done.

Reconnect (both): §3.4 procedure, then resend every unacked outbox entry with the same
`clientMessageId`.
